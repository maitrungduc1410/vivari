The fastest way to fake a package manager in a browser is to write one. Read a
`package.json`, resolve the tree against the registry API, download tarballs,
untar them into `node_modules`. A few hundred lines and it works for most
projects. We shipped exactly that, and called it what it was: a temporary
stand-in.

StackBlitz did the same thing. Their custom client, Turbo, shipped in 2018 and
was deprecated in April 2024 in favour of the real npm, yarn and pnpm. That arc
is not a coincidence — it is what happens when you discover how much of the
ecosystem depends on the actual CLI rather than the idea of one.

Lockfile formats you did not implement. `overrides` and `resolutions`.
Workspaces. Lifecycle scripts in the right order. `.npmrc` resolution.
`peerDependenciesMeta`. Every one of those is a support request, and each one is
a small reimplementation of behaviour that already exists in a program you could
have just run.

So the goal was never a better installer. It was to run the real ones.

## npm: booting is the easy part

The first milestone was not `install`. It was `npm -v` printing `10.9.2` and
exiting 0. That alone exposed three genuine Node-fidelity gaps:

- **`process` must be a real `EventEmitter`.** npm's logging goes through
  `proc-log`, which attaches listeners to `process`. Our `process` was an object
  with some properties on it. Close enough for user code, not close enough for
  npm.
- **`import()` inside CommonJS must route through the loader.** npm does
  `await import('chalk')` from CJS. A dynamic import that reaches the browser's
  native module loader instead of the runtime's resolver finds nothing.
- **Exit semantics must be exact.** `stdout.write(cb)` firing its callback,
  `process.exitCode` being honoured, and `'exit'` emitting exactly once. npm's
  exit handler is picky, and a double-fired `'exit'` produces confusing
  half-completed installs.

None of these are npm-specific bugs. They are places where our runtime was
approximately Node, and npm was the first program strict enough to notice.

Real installs came next: rebuilding `lib/https.js` as a fetch-backed client so
that npm's own `npm-registry-fetch → make-fetch-happen → minipass-fetch` stack
runs unmodified. Then lifecycle scripts, `.bin` linking, and `npm exec`.

The one genuinely unsolvable case was **native builds**. A package whose
`install` script is `node-gyp rebuild` cannot work: there is no compiler
toolchain in a browser tab, and there never will be. What we could fix was the
blast radius. Previously one native dependency aborted the entire install. Now
`node-gyp` is stubbed to a no-op that warns and exits 0, so the package's
JavaScript or `wasm32-wasi` fallback is what loads at runtime and
`preinstall` → `install` → `postinstall` completes.

That is a deliberate trade, and worth stating plainly: we make native
compilation a **non-fatal skip** rather than a hard failure. Packages that
genuinely require a native addon will not work. Packages that ship a fallback —
which is most of them now — will.

## Delivery: the boring problem that ate the most time

Here is a problem that does not exist on a server. The browser cannot
`readdirSync` your machine, so before you can run npm you have to *get npm into
the virtual filesystem*.

npm is about 2,400 files. Fetching those individually is absurd, so the build
packs the whole pinned tree into a single gzipped asset, decodes it in the
browser with the platform's own `DecompressionStream`, and unpacks it into the
filesystem at `/usr/lib/node_modules/npm`.

The detail that cost an afternoon: the asset is named `npm-pack.bin`, not
`npm-pack.gz`. Static hosts see a `.gz` extension and helpfully apply
`Content-Encoding: gzip`, so the browser transparently decompresses it — and
then our code decompresses it again, on data that is no longer compressed. The
fix is to stop advertising the compression in the filename.

After the first boot the unpacked tree is persisted to OPFS, so later boots only
need to reapply a couple of thin shims that point `/bin/npm.js` at the real CLI.

## yarn: five bugs, one of them structural

yarn classic is small to deliver — essentially `bin/yarn.js` plus a ~5 MB
webpack bundle. That 5 MB is itself informative: it does not fit through the
[1 MiB shared-memory window](/blocking-in-a-browser), so it has to go
through the transferred-buffer path instead.

Running it filled five gaps npm had not touched:

1. `process.stdout` and `process.stderr` needed the full EventEmitter and
   Writable surface — `prependListener` and friends — that yarn attaches during
   bootstrap.
2. `process.memoryUsage()`, because yarn's reporter tracks peak RSS.
3. A legacy `process.binding(name)` shim delegating to `internalBinding`, for
   yarn's bundled `safer-buffer`, `builtin-modules` and `constants`.
4. Two lazy `fs` internals — `internal/streams/fast-utf8-stream` and
   `internal/fs/dir` — that yarn trips by *merely enumerating* every getter on
   `fs`, via `thenify-all`'s `promisifyAll`. Nothing called them. Reading the
   property was enough.
5. The structural one.

That last one is worth spelling out, because it is a perfect example of what
"exactly right" means when you are
[shipping Node's real source](/nodes-real-lib-in-the-browser).

`internal/fs/streams` defines `ReadStream` and `WriteStream`. We had written
them as ES6 `class` declarations, which is what any modern engineer would do.
Real Node defines them as ES5 function constructors — callable without `new`,
initialising via `Readable.call(this)`.

`graceful-fs`, bundled by yarn and by fs-extra and by half of npm, subclasses
them the old way:

```js
fs$WriteStream.apply(this, arguments);
```

You cannot `.apply()` a `class`. It throws `TypeError: Class constructor cannot
be invoked without 'new'`. The fix was to stop writing modern JavaScript and
write what Node writes.

There is one known cosmetic wart we have not chased: yarn prints "You don't
appear to have an internet connection", because its connectivity probe is
DNS-based and our networking is fetch-backed. The install then succeeds anyway.

## pnpm: the one we expected to fail

pnpm looked like the wall. It does two things that a browser runtime has no
business supporting.

It uses **real worker threads** — `dist/worker.js` for fetching and extracting.
And it builds a **symlinked** `node_modules`, where `node_modules/<pkg>` points
into `.pnpm/<pkg>@<version>/node_modules/<pkg>`, so module resolution has to
traverse symlinks correctly or nothing resolves at all.

Both worked unmodified.

The worker threads work because the process model already runs each process as a
Web Worker; nested threads are just more of the same. The symlink store works
because the Rust virtual filesystem implements `symlink`, `readlink` and `lstat`
properly, with an `ELOOP` guard — which was built long before anyone was
thinking about pnpm.

The only gap was `util.types.isBoxedPrimitive`, a single missing function on
pnpm's registry JSON path.

This is the most encouraging result in the whole project, and the reason is
worth naming: the components that survive contact with software you did not
anticipate are the ones that implemented a *real specification* rather than the
subset you happened to need. A virtual filesystem that supports symlinks because
POSIX has symlinks handles pnpm on the first try. One that supports the
operations your test app used would not have.

## What this actually proves

Every one of these bugs was generic. `process` becoming a real EventEmitter,
ES5 stream constructors, `process.binding`, `isBoxedPrimitive` — none of them
are package-manager features. They are Node behaviours that our runtime had
approximated, and the package managers were simply the first programs demanding
enough to find them.

That is the argument for running real software as your test suite. A
hand-written conformance test checks what you thought to check. npm checks what
npm needs, which is a much better-informed list.
